One of the best things about the Lisp Family of Languages is how easy
it is to create a new dialect of Lisp which meets your personal ideal
of a programming language.

One of the worst things about the Lisp Family of Languages is how many
different and slightly (or majorly) incompatible dialects of Lisp
there are.  This is bad because it interferes with being able to share
good code with fellow programmers using a different dialect!

- [[https://xkcd.com/927/][XKCD on Standards]]

It's always educational to create a new Lisp for private
enlightenment.  Releasing such a creation to the public and advocating
its use should not be done casually!

** Removing Unnecessary Restrictions

#+begin_quote
Programming languages should be designed not by piling feature on top
of feature, but by removing the weaknesses and restrictions that make
additional features appear necessary.

-- [[https://conservatory.scheme.org/schemers/Documents/Standards/R5RS/HTML/][Introduction to the 5th Edition of Scheme]]
#+end_quote

One of the greatest revolutions in Lisp was the development of Scheme, a new Lisp which was
- More powerful than any previous Lisp
- Simpler than any major previous Lisp

Scheme was designed in 1971!
- It's had huge influence in later Lisps, yet
  - Most later Lisps are less powerful than Scheme!
  - Most later Lisps are more complex than the original Scheme
    - Including later "editions" of Scheme!

We've learned a lot since 1971!
- Some of this learning has become new Programming Language Features
- Making Programming Languages more complicated

Much of what we've learned since 1971 (and even before)
- Has NOT been added to the major popular Lisps!
- This presents a huge opportunity!

It would be worth creating a new Lisp if
- It is no more complex than existing popular Lisps
  - Especially the latest edition of Scheme
- Has great support for the missing advances pioneered by
  - Other Lisps
  - Other radical Languages
  - and some bits of theory!

      - With Compile-Time Dimensions and Units
      - With runtime Error Propagation Tracking

      - Manifest or inferred Abstract Types

      - General efficient pattern matching for code and data
      - Principle of Least Power providing choice of computation models
            - Regular, Functional, Relational Programming
            - Datalog, Logic and Declarative Constraint Programming
            - Staged Metaprogramming

      - Programs specified abstractly
            - Operations on Streams and Collections
            - Parentheses in Symbolic Expressions would not imply Linked Lists

            - Human suggestions checked and applied where safe and useful

      - or perhaps special braces for the form

      - Browse code with unwanted details suppressed
      - Provably correct refactoring
      - Logical debugging
